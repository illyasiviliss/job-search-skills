# 主张一致性审计 ＋ 占位符兑现法

> 触发：用户把 `02 待补事实` 填完；或用户说「你当我做过」「数字随便标」；或用户给了一个新的自建项目。
> 本文件只管**审计做法**与**把占位符变成真数字的流程**；怎么跟用户对齐「写到多满」见 SKILL.md 的「简历策略」一节。

## 一、一致性审计（填完 02 之后必跑）

不要只把空填上就完事。跑一遍「**母版已写的主张 × 用户本人的回答**」对照，把**写了但用户答不出来**的内容挑出来。

| 母版位置 | 现在写的 | 用户的回答 | 后果 |
|---|---|---|---|
| 第 8 节 技能栏 | 写上去的一串工具（如 Python / SQL / BI 工具） | 实际只用过其中一部分 | 技能栏是面试官第一个拿来出题的清单 |
| 某段经历描述 | 「基于 <工具> 构建 <模型>」 | 该工具无实操 | 会照这句往下追问 |

**技能栏是最危险的一栏**——它是面试官逐条出题的清单；经历描述里的工具与职责是第二危险的（会顺着追问）。

### 三类处置，逐条交用户定，不自行删改

1. **撤下** → 改可见性标签为 `[存档]`。**母版留料，只是不进导出版本**（用户说「以后有什么岗位需要再用」时这条路正好）。
   撤下的条目不需要数字 → 「随便标数字」往往已经没有适用对象，先把这一点讲清楚。
   ⚠️ 撤下的段里若还有 `[待补：…]`，校验脚本照样阻断。把它改写成普通中文备注（`（存档，数字未核实）`），**不要**为了过脚本而填猜的数字。
2. **改写** → 换成用户**真做过**的动作与工具（工具降级、动作保留）。真实且更可信。
3. **保留 ＋ 兑现时间线** → 用户选择保留原样时，在母版里加一条 `>` 内部备注，写清：事实核实结果、逐格变真的时间表（哪一天哪一格能写）、以及到期要做的对齐复核。**不要**在正文里加「基础」「了解」这类限定语。

审计出的降级结论要**当次**写进真实画像（→ `job-search-method` 维护），别停在「待确认」。

## 二、占位符兑现法（替代「编」的可执行做法）

用户要的是「先有东西撑起简历」，这在三条件下是可以做的：

1. **先立项**（写进 `07 投递台账` 或专属项目文件，含里程碑与验收标准）；
2. **按完成态起草条目**，但每个数字写 `XXX` 占位 —— `XXX` 不是编造，是**待兑现**；
3. 拿到真实产出的**当天**替换，并把那一天写成「**第一批真数字可用日**」——从那天起才开始投练手公司。

**优先让项目在早期就产出一个真数字**（例如先把采集量做到三位数），不必等项目全部完成才有可投的版本。

### 自建项目的数字是用户自己数出来的

抓取／统计／自建管道类项目，面试官问「这个数怎么来的」对用户是**加分题**而不是陷阱。
明确告诉用户这一点：这是你唯一能答得比所有候选人都好的地方，别把它做成答不出来的。

## 三、项目选题判据（第 5 节空白时用）

按重要性排：

1. **每个数字都能被用户本人追问到底**（数据是用户自己采的、自己清洗的）。
2. **避开样本量 n=1 的自数据类项目**（分析自己的日志/健康/行为）—— 面试官一句「一个人能得出什么统计结论」就讲不下去了。留作工程侧小作品可以，不做主项目。
3. **外部数据 ＋ 真实业务问题 ＋ 用得上技能栏里的工具**（Python / SQL / BI 一次全占）。
4. 15 天做得完：抓取这类机械劳动由 agent 包，用户负责建库、查询、结论。
5. 结论要能**反过来指导用户自己的决策**（这种项目在面谈里最好讲，也最容易被记住）。

里程碑按「立项与数据源 → 抓取 → 建库清洗 → 分析 → 看板交付」五段排，每段给一个可指认产出与验收标准。

## 四、让简历上的自建项目「有实感」：先把真工程骨架搭起来

**用户判断一个东西算不算真项目，标准往往是「有没有工程骨架」。**
所以简历上只要写了自建项目，就**先把骨架搭起来，别等项目做完**；空目录也不算，得把已经产出的真资产搬进去。

骨架放在 `~/Projects/<英文 slug>/`（目录名用英文，将来要挂 GitHub）：

```text
<slug>/
├── README.md         # 一句话是什么 / 现在到哪一步（模块状态表）/ 目录结构 / 快速开始 / 面试会被问的口径表
├── src/              # 编号脚本：00 接收、01 取数、02 建表、03 筛选…
├── data/raw/         # 原始响应（gzip 归档，只读）
├── data/processed/   # 清洗后的产物
├── docs/             # 数据字典（字段 ID→中文名→选项标签）＋ 方法说明
├── outputs/          # 对外交付物
└── logs/<日期>.md     # 当天操作记录 ＋ 踩过的坑
```

三条硬要求：

1. **搬真资产进去**（原始响应、清洗脚本、CSV、短名单、xlsx）。没有真数据的骨架给不了实感。
2. **从文件夹里重跑一遍管道并核对结果**（例：`python3 src/03_*.py` 能否重产出同一份名单）。**可复现才算项目**；跑不通就先修到能跑，别只摆结构。
3. `git init` ＋ 一次真实 commit，`.gitignore` 排掉 `data/raw/` 这类大文件。这是简历里「可验证链接」的落点。

顺带产出两份面试答案材料（面试高频两问的现成答案）：

- `docs/方法说明.md` 里的「**人的部分 vs AI 的部分**」分工表 → 答「你做的 vs AI 做的怎么分」。
- `logs/<日期>.md` 的**踩坑记录**（格式/鉴权/编码/口径这些试错轨迹）→ **AI 编不出来的痕迹**，被问到时直接讲。

搭完**替用户打开**（`open -a "Visual Studio Code" <路径>`），别只报路径。

## 五、别把二手汇总当自采数据源

从公众号／电商店买来的校招汇总表（xlsx ＋ 飞书/腾讯文档）是**候选池与对照集**，不是数据源。
项目条目若写「自建数据采集流程」，拿别人整理好的表去分析会让那句话变成假的 —— 一手源还是要自己抓，汇总表只用来验证覆盖率。
