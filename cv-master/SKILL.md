# 简历母版（CV Master）

一份母版做唯一真相源，简历版本是它的衍生物。**不要**反过来从某份投递版回写母版。

## When to Use （何时使用）

- 用户说「更新我的简历 / 加一段经历 / 我换工作了 / 我拿了新奖」。
- 用户要「总结一下我的能力 / 我能投什么岗 / 我简历有什么问题」。
- 用户问「我可以投哪几个板块 / 往哪个方向投 / 这些岗位来源靠谱吗」→ 主流程 E。
- 对着某个 JD 说「帮我改一版简历 / 定制一版」。
- 要把简历导出成 Word 或 PDF 发给别人。

不适用：替用户投递、群发、写求职信（除非明确要求把求职信也纳入本次任务）。

## 文件布局

母版根目录 `$CV_MASTER_ROOT`，默认 `~/Documents/Career`（首次使用若不存在则创建，并静默完成，无需询问）。

```text
Career/
├── 母版.md              # 唯一真相源
├── 素材/                # 未采用的子弹点、原始材料、旧版 PDF
├── 投递/<公司>-<岗位>/  # 定制版输出（Markdown + 导出的 docx/pdf）
├── 导出/                # 通用中/英文正式版
└── .backups/            # 写入前的快照，保留最近 10 份
```

先读 `母版.md` 再动手。找不到就用 search_files（target='files', pattern='母版.md'）定位，或报出它不在默认位置让用户确认，**不要**自己新建一份覆盖。

**对外 / 对内分离（硬规则）**：母版是**对外材料**，其中的措辞不等于用户的真实水平；内部分析（能不能拿到面试、缺口在哪、值不值得投）另建独立文件，本技能**不回写**它们。

**进度面板（可选但推荐）**：动手前先更新它，收尾也更新它——别让聊天里的进度留在聊天里。若用户用 Obsidian / Notion / 纯 Markdown 记录进度，面板里放：板块状态 / 卡点 / 评估分 / 相关文件路径；文件名带主题后缀，**按前缀编号定位，用 search_files 找，别背全名**。

## 母版结构（固定 12 节）

0 维护说明 / 1 基本信息 / 2 求职目标 / 3 教育 / 4 实习 / 5 项目 / 6 校园活动 / 7 获奖 / 8 技能 / 9 语言证书 / 10 能力画像 / 11 素材库 / 12 版本记录。

空白模板见 `references/master-profile-template.md`。新增小节时保持编号连续；不要为了「好看」重排编号，
**也不要把新内容挤进已有编号**（例：为放「个人总结」而把第 2 节「求职目标」改名，会同时造出两个第 3 节）——
其他文件按「第 5 节 / 第 10 节」引用，重编号会静默打断这些引用。新内容要么并入最相关的那一节，要么另起一个不被数字引用的标题。

## 可见性标签

每条经历、每个子弹点都带一个标签，决定它进不进某个版本：

| 标签 | 含义 |
|---|---|
| `[常驻]` | 所有版本都放 |
| `[按岗]` | 只在相关岗位的版本放 |
| `[按需]` | 被问到、或版面有余量时放 |
| `[存档]` | 保留但不主动放 |

标签随经历一起维护。定制版本时先按标签筛，再按相关性排。

## 主流程 A：摄入 / 更新经历

1. **读母版**，确认要改的是哪一节、哪条。
2. **一次问清事实缺口**（不要挤牙膏）：时间起止、组织全称、确切角色、团队规模、负责范围的数字、结果数字、哪些是他做的、哪些是团队做的。
3. **数字缺失就写占位** `[待补：XXX]` —— 禁止编造、禁止用「显著提升」这类无证据的形容词。
4. **起草子弹点**：动词开头 ＋ 做了什么 ＋ 用什么方法/工具 ＋ 可量化结果。一段经历 2–4 条，最重要的放第一条。
5. **备份**（`scripts/backup_profile.sh`）→ **展示 diff 给用户看** → 确认后才写入。
6. **同步**：更新第 10 节能力画像、第 12 节版本记录各追加一行。

## 主流程 B：能力汇总

输出三块，按能力族组织（分类参照 `references/ability-taxonomy.md`）：

1. **能力族清单** —— 每条结论后面必须挂证据（哪段经历、哪个数字）。没有证据的能力不写。
2. **与目标岗位的匹配** —— 若给了岗位/JD，逐条对照；没给就按主方向默认对照。
3. **缺口** —— 明确写出「没有公开证据支撑」的能力，供面试准备与补强。

汇总结果写回母版第 10 节，替换而非追加，保持它是一张快照。

## 主流程 C：定制版本 / 导出

写法细节见 `references/writing-playbook.md`（成就优先、量化、岗位技能维度、页数控制、summary）。

1. 读母版 ＋ 目标 JD。
1b. **先定语言，别默认**：英文工作环境的公司（JD 用英文）→ **英文版**；中文校招系统（官网／公众号／招聘 App 投递）→ **中文版**。同一目标不必中英都出，除非用户要求。
2. 按可见性标签 ＋ 相关性选条目，重排顺序（相关经历上移）。
3. 改写摘要与技能栏，让关键词对标 JD；**只允许换措辞和排序，不允许改事实**。
3b. **JD 加权选配**：把 JD 要求逐条列出并按重要性打 1–10 分；给母版每条成就对每个高权重要求打相关分；按「相关分 × 要求权重」排序选条（JD 里出现越多的关键词，对应成就越靠前）。只改选择与顺序，不改事实。
4. 输出 Markdown 到 `投递/<公司>-<岗位>/`。
4b. **校验阻断不等于不干活**：脚本退出码 2（有 `[待补]`）时**照常产出 Markdown 定制版**，只在文件尾注明「未导出：阻断原因 ＋ 待补项」并把需用户补的事实列成表。**不要**因为不能导出就不做定制版，也不要为了让脚本通过而删掉 `[待补]` 或填猜的数字。
5. 导出（命令与依赖见下）：

```bash
# MD → DOCX（pandoc 路径；在 Word 里还要微调时用）
pandoc 输入.md -o 输出.docx

# 收紧成 A4 一页版（pandoc 默认 Letter ＋ 12pt，中文简历必然溢出到第 2 页）
python3 scripts/tighten_docx_a4.py 输出.docx [--size 19] [--margin-tb 600]

# DOCX → PDF（pandoc 自身没有 PDF 引擎，需要 LibreOffice）
soffice --headless --convert-to pdf --outdir <输出目录> 输出.docx
```

先跑 pandoc 出 docx，再拿 docx 转 pdf —— 直接 `pandoc -o x.pdf` 会因无 PDF 引擎失败。
导出失败时说清是哪一步、缺什么，**不要**伪造文件已生成。

### 页数与填满度验收（要求一页就必须真的数出来）

```bash
python3 -c "from pypdf import PdfReader; print(len(PdfReader('输出.pdf').pages))"
sips -s format jpeg --resampleWidth 1100 输出.pdf --out /tmp/preview.jpg   # 用视觉检查排版
```

- **跑生成器／量页数一律用 `terminal`，不要用 `execute_code`**：`pypdf`、`pymupdf` 常装在系统 python 里，而某些沙箱 python 里 `import pypdf` 会 `ModuleNotFoundError`，页数与填满度全变成 `ERR`（不报错、静默降级，最容易漏看）。
- **必须真的数页数**（`pypdf` 可用；`mdls kMDItemNumberOfPages` 在 macOS 上常返回 null，别用它）。
- **填满度要量，不能眼看。** 用 `pymupdf` 取正文最低点 ÷ 版心底部（A4 842pt − 下边距）。目标 **1 页且填满度 92–96%**；低于 90% = 底部留白偏多，往上调一档字号再跑。溢出到第 2 页时按这个顺序收：调小字号 → 收边距 → 删 `[按需]` 段。
- **溢出时先量「差几行」，再决定砍什么 —— 不要盲砍。** 用 `scripts/measure_content_height.py <某版.html>` 量内容真实高度（pt），与版心高度比。**必须留 ≥20pt（约 1.5 行）余量**：屏幕上看着「没溢」不代表打印不翻页，打印重排会把临界内容挤出去。知道差几行才选得对手段：差 1 行改一条 bullet 的字数，差 3 行才动字号（字号每降 0.2pt 约省 2% 总高）。
- **收紧后一定用视觉看一眼**渲染：中文字体是否被替换成方块。

### 中文字体与 ATS（踩过的最贵的坑）

**中文字体必须挑「PDF 里能正确提取的」——这一条直接决定 ATS（申请人跟踪系统）能不能读到关键词。**

用 `Songti SC` ／ `STSong` ／ `SimSun` ／ `PingFang SC` ／ `Hiragino Sans GB` ／ `Microsoft YaHei` 出的 PDF，约 **4–5% 的汉字会被 pypdf 抽成 Kangxi 部首码位**（`⼴东`、`圣⽕`、`⼤学`、`⼯作`、`项⽬`、`⾏业`、`⾦融`、`⽤`、`⼈`、`⼀`……）。**肉眼完全看不出来**（渲染是对的），但 ATS 关键词匹配一个也命中不了——尤其撞公司名、学校名、「项目」「工作」「行业」这类高频词。

实测**能干净提取**的字体：`STHeiti`、`STFangsong`、`STXihei`、`Lantinghei SC`、`Yuanti SC`、`Arial Unicode MS`。
一个可用的组合：`"Times New Roman", "STHeiti", "Arial Unicode MS", sans-serif`——Latin 走 Times（保留传统衬线观感），中文落到 STHeiti（黑体，比宋体更干净现代）。

**改字体后必须验**：抽 PDF 文本，数 CJK 部首区间（`0x2E80–0x2FDF`）的字符数，**必须是 0**：

```bash
python3 -c "from pypdf import PdfReader; t=PdfReader('x.pdf').pages[0].extract_text(); print(sum(1 for c in t if 0x2E80<=ord(c)<=0x2FDF))"
```

这个检查开了以后，「内容里有没有混进不该有的词」的核验才真的有效（字体坏时文本都抽不出来，检查会假报「无」）。

### 渲染坑（都踩过）

- **Markdown 里 `**粗体行**` 后面紧跟 `-` 列表，中间没有空行 → pandoc 判为同一段**（lazy continuation），渲染出来要点全挤成一行、项目符号全丢。**粗体小标题与列表之间必须留空行。**
- 同一段内想换行要用**行尾两个空格**（硬换行）；直接回车在 pandoc 里等于空格。
- **HTML 里不认 Markdown**：用 HTML ＋ Chrome 出版时，`**粗体**` 会原样打印成字面上的星号。要加粗写 `<b>`。改完**用 pypdf 抽正文核一遍**有没有残留 `**`。
- **不要用 Chrome `--screenshot` 截 HTML 判断填充度**：HTML 没有 `@page` 约束，截图里的比例与 PDF 里根本不是一回事。要判断版面，只量 PDF、只看 PDF 渲染出来的图。
- **逐档试字号时不要把测试输出写进正式产出目录**：写进去的话，最后一档测试结果会冒充正式产物。要么写到临时目录，要么试完**必须重跑一次真正的生成器再验收**。

导出成 docx 后如果母版改过，重新导出，不要让两份文件内容漂移。

### 版式：先找参照物，再做

**动手排版前先找参照物**：用户给过、或历史上产出过的 CV 就是目标样式。找不到就在下载目录、素材目录里翻旧 PDF/DOCX，用 `sips` 转 JPEG 看一眼版式；**没有参照物就先问用户要一张，别自己发明一套**。

**通用版式基线**（招聘端接受度最高的一套）：纯黑、无灰、无彩色；单栏；节标题全大写 ＋ 下划线；机构名粗体靠左、日期粗体右对齐（同一行）；职位用斜体；**整页 A4 填满，底部不留大片空白**。

**会被判为「难看」的做法**：节标题做成灰色小字、底部留 15% 白、姓名与定位语同字号、联系方式挤成三行还断行。姓名必须显著大于正文，定位语紧随其下。

**删内容之后要反手把字号放大填回来。** 拿掉整节内容后，同一套 CSS 可能只剩四成高度 —— 一页简历留半页白很难看。做法：**结构不动，只把 `body` 字号往上调，重跑，再量**；这个阈值是**非线性**的（可能 9.6pt 正好一页，10.4pt 立刻溢到第二页），必须逐档试、不能插值猜。

**字号与页边距是下限，不是可调参数**：正文 **≥10pt**、页边距 **≥0.5 英寸（12.7mm）**（全套硬指标见 `references/resume-format-standards.md`）。**正确的收版顺序是「先砍内容 → 再定字号」**：把每条要点压到 1 行（中文 ≤50 字）腾出空间，然后把字号提回 10pt，而不是反过来压字号去迁就内容。

**顺序是硬要求：先把内容定死，再做版式。** 用户说「先定好内容，再做 pdf 的排版」时不要抢跑——内容还没落定就排一版给他看，等于把返工写在前面。内容定稿前只讨论字句、取舍与顺序。

**技能栏不要做成表格**：两列表格只装三行内容会在右侧留一大片空白。用「分类：内容」的三行普通段落。

### 写法层（内容质量）

- **技能栏不抄课程大纲的章节名。** 把 syllabus 目录搬上去（「描述统计、概率分布、抽样与抽样分布……」）是**细**，不是**专**，读起来像在背教材目录。做法：用**招聘启事里真正出现的词**分三到四类（如「语言与工具 ／ 分析方法 ／ 数据工程与交付」），总长压到 3–4 行、每行 40–70 字；课程覆盖到的范围写宽一档。**语言不必单独占一行**（若已有「语言与证书」节会重复）。
- **多个项目必须类型不同。** 项目要展示**跨度**而不是重复：两个项目若都写成「采集 → 清洗 → 入库 → 分析」，读者看不出差异。定式是一**分析型**（SQL-heavy，落点是「我从数据里得出了什么结论」）＋ 一**工程／产品型**（落点是「我做了个能跑起来、别人能看的东西」，配 GitHub 链接）。两边都补**数据集规模**数字（行数 × 字段数、覆盖家数、信息源类数）——这是初级候选人最守得住的一类数字。
- **教育段的「相关课程」是用来证明「我学过跟这个岗位有关的东西」，不是展示分高。** 拿成绩单逐门筛，按「**课程内容 → 简历里哪一段经历**」对齐，**分数只挂在相关的课上**；不相关的课，分再高也不占位置。**篇幅硬约束：这门课行必须压在一行内（约 50 字符）**——教育段是多版共用的常量，它多占一行，**所有版本会一起从 1 页溢到 2 页**。写完必须重跑全部版本数页数，不能只跑自己正在看的那一版。
- **经历段不写实现细节，只写口径层。** 「（同一用户短时内的连续重复动作合并计 1 次）」这类做法描述、以及「扫码率 = 扫码量 ／ 出货量」这类公式写法，读起来是「细」不是「专」。抬到「统一多源字段口径」「定义核心指标口径」「按区域分群对比并做归一化」——说「我定过口径、我做过分群」就够了，实现细节留给面试口头讲。
- **同一件事实不要在两条经历里各写一遍。** 重复是「看不出差异」的主要来源。
- **段落权重：实习段必须比项目段重。** 量法：抽 PDF 文本，比 `INTERNSHIP`→`PROJECT EXPERIENCE` 与 `PROJECT EXPERIENCE`→`SKILLS` 两段的字符数，实习段约 1.3–1.5 倍于项目段。**要腾空间先砍项目**（个人项目**封顶 2 个**、每个 2 条要点、字数压短），不要砍实习。
- **bullet 句子公式**：**动作动词 ＋ 具体工作 ＋ 点名工具 ＋ 有范围的产出**。动词按职能取：分析 analyzed/segmented/modeled，数据处理 queried/cleaned/joined/validated，构建 built/automated/designed，沟通 visualized/reported。

**做法选择**：

- **要像素级还原某个版式（默认情况）→ HTML ＋ CSS，用 Chrome headless 打印成 PDF**。比 pandoc 可控得多（右对齐日期、下划线节标题、字号行距全掌握）。命令、可直接抄的 CSS 与调参顺序见 `references/layout-and-pdf.md`。
- **另需一份可编辑 Word**：`textutil -convert docx -output x.docx x.html` —— 从**同一份 HTML** 转，避免两份内容漂移。pandoc → `tighten_docx_a4.py` 那条路保留给纯 Markdown 场景。

### 多版本简历（同一套事实，多套讲法）

用户要「按不同岗位类别出几个版本」时：

- **事实只有一套，改的只是选哪些面、放第几位、用什么动词**。逐版措辞的依据先写成一张「**岗位类别 × 项目能力映射**」表，再动笔。
- 生成器只认一份，且**机器上只留一份真文件**。两份脚本各改一半会造成漂移：脚本看着是新的，产出还是旧的。定式：canonical = skill 内的 `scripts/gen_cv_versions.py`，另一个位置放三行 `runpy.run_path(...)` **转发脚本**，脚本内不写任何逻辑。这样用户想双击那份也能跑，而两份不可能再分叉。版本内容以 dict 写在脚本里，一次跑出全部版本的 HTML ＋ PDF，**并自动打印每版页数**。
- **动手前先确认「跑哪个脚本」，并比对产物与脚本是否一致。** 若产出的 HTML/PDF 里有脚本里没有的字符串（定位语、技能行、整节内容都对不上），说明这些产物曾被手工改过 —— 那就**以现实产物为准，把脚本重写一遍**，之后只认脚本。反过来改 HTML 是死循环：下次重跑，手工改动全丢。
- 每版差异固定在**三处**：**抬头下的定位语、个人项目的顺序与详略、技能栏首行（含条数）**。其余段落各版共用同一份字符串。
- **用户要看就先给一版，别一次丢四个。** 先跑通 MVP：`python3 gen_cv_versions.py V1`（`V1 V3` 也行，不给参数才出全部）。**多产物任务都按这个节奏**：先出一份样品 → 用户点头 → 再全量重出。
- ⚠️ **改了共用段落（实习段、教育段）之后，其余版本的 PDF 立刻变成过期产物。** 要么马上全量重跑，要么**主动说明「V2–V4 是这次改动之前的」** —— 绝不能让用户以为都更新过了。
- 生成器里「某次改动后不再引用」的 dict 会留在文件里，看着像还在生效。**改完顺手确认每个 dict 都被某个版本引用**，孤立的要么删掉要么加注释说明为何保留。

### 给用户的「可编辑工作台」（他反复要的那种）

用户想自己改内容时要的是**可编辑工作台**，不是母版本身：

- 建一份独立笔记（如「NN <主题>工作台.md」），**结构 ＝ 最终产物的顺序**，一块一段。
- 每块两层：**「排版提示」**（写这段在成品里怎么呈现，并声明「你不动也行」）＋ **「✍️ 内容」**（他要改的字；明说「不想要的行整行删掉」）。
- 若是**策略层**工作台，则每块改为 **「现状（我的理解）＋出处」＋「✍️ 你的策略（改这里）」**——他指出错哪句就直接改那段，不要只留空白让他从零写。
- 母版仍是唯一真相源：**他改工作台 → 你回写母版 → 再排版**。明确告诉他「别同时改母版和工作台」。
- 母版里的内部账本段（如第 0／10／11／12 节）**不要塞进工作台**，只说一句「那些是内部账本，不进导出」。
- 建好**替他打开**（Obsidian 用 `obsidian://open?vault=<vault>&file=<路径>`，路径要 URL-encode）—— 别只给路径让他自己找。

**三层结构（推荐形态）：主工作台（事实库）＋ 按岗位方向的子工作台**

- **主工作台**＝「我做过什么」。只放事实与素材（抬头／摘要素材／教育／实习／个人项目／课程项目／技能素材／获奖证书／**真数字库**／待办），**不分版本、不排序、不针对岗位**。改内容只改它，所有版本一起变。
- **子工作台**＝每个岗位方向一份。每份只决定三件事：**用哪些块、排第几位、换什么措辞**，外加该版的定位语、摘要（若用）、技能栏首行、取舍说明与「面试重点准备」。
- 主工作台里**每条素材要带出处**（哪个文件／哪节课作业／哪个项目）——被追问时的落点。
- 主工作台单列一张**真数字库**：只写真值，每条标来源与状态（`✅ 真` / `⏳ 待测`）；顺手在别的产物里发现可用真数字时**立即回收进来**，别让简历里留着 `XXX`。
- 引用链：**主工作台（内容源）→ 子工作台（讲法）→ 母版（导出源）→ 生成脚本（产出）**。任何一处改过都要向下同步。

## 简历策略：两条路线，先与用户对齐（**动手前先定**）

写简历有一个绕不开的取舍，**先问清用户选哪条**，再决定措辞强度。两条都成立，代价不同：

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 饱和式写法** | 措辞、强度、覆盖面拉满；把「能覆盖到但还没完全落地」的技能也写上 | 面试会问到答不出来的层级 → 必须配套「技能追问演练」（见下） |
| **B. 保守式写法** | 只写能完整讲清的内容 | 通过率打折，可能连面试都拿不到 |

- **选 A 时不要自我降级**：不要主动建议删词、加「基础／了解」限定语、降低强度。措辞诚实与否是用户的决定，本技能只执行。
- **选 A 的必要配套是「技能追问演练」**：把简历里每句可能被追问的话拆成三档（**1 名词 / 2 机制 / 3 取舍**），标出当前层级、缺口与补法。演练表不是折中方案，是 A 路线的组成部分；每次面试后把「被问穿的是哪一句、问到第几层」回填进去 —— 这就是「用真实面试当校准器」。
  **分工**：演练表管「我这句话会被问什么」；面试本身的备战见 `interview-prep` 技能。
- **两条路线共有的唯一约束：不「新增」编造内容**（不写未发生的事、不虚构头衔与时间）。
- **用户想写一个「现在还没做」的项目时**：把两条路摆清让他自己选 —— ① 永不兑现，不做；② **先立项 → 按完成态写 → 限期兑现**，数字用 `XXX` 占位，拿到真实产出当天替换，并给出「第一批真数字可用日」（第一个里程碑那天）。**一句话说完，不要展开论述。**
- **撤下的经历不需要数字**：先确认那条是要撤还是要留。

> **自建项目（抓取／统计类）的数字是用户自己数出来的** → 面试官问「怎么数的」是**加分题**，不是陷阱。
> 明确告诉他这一句：这是你能答得比所有候选人都好的地方，别把它做成答不出来的。

**一致性审计仍然做，但只作内参**：把「母版主张 × 用户本人的回答」对照，把已写进去但答不出来的内容写进内部画像与追问演练表 —— **不要据此去劝他改母版措辞**（除非他选了路线 B）。做法与项目选题判据见 `references/resume-claims-audit.md`。

## 主流程 D：体检 + 校验（先跑脚本，再上眼）

用户说「看看我简历有什么问题」、或任何导出前的最后一道闸，都走这条。

1. **机器校验**（只读，不写文件）：

   ```bash
   python3 scripts/validate_profile.py             # 默认 ~/Documents/Career/母版.md
   python3 scripts/validate_profile.py 某投递版.md  # 也可校验任一版本
   ```

   退出码 **2 = 有待补未清或编造风险词，禁止导出**；0 = 通过。
   输出六块：待补标记 ｜ 无证据形容词 ｜ 量化事实清单 ｜ 实体清单（只读锁）｜ 联系方式 ｜ 分节统计。
   第 3、4 块是给改写着用的：**改写时数字和实体逐一对齐这张清单，不得新增**。
   阻断项以脚本输出为准：别凭印象估「应该没几处」，数量与位置一次跑清，再按「真正影响投递的」排优先级。

2. **人眼体检**（脚本抓不到的结构问题）：对照 `references/writing-playbook.md` 第 7 节五项。
3. **出问题清单**：分「阻断级 / 结构级 / 表述级 / 一致性」四档，每条给「问题 + 在哪 + 怎么改 + 需用户补什么事实」。
4. **评估闭环**：按 事实完整度 / 量化强度 / 结构 / 岗位适配 / ATS / 表述力 六维给粗分，标出主要失分点，供下次对比。
5. 体检只读不改数据；要改则走主流程 A（备份 + diff + 确认）。

## 主流程 E：板块定位 + 渠道自检

用户说「我可以投哪几个板块 / 往哪个方向投」时走这条。结论同时写进进度面板，别留在聊天里。

1. **先问边界，再给板块**（不问就给的板块表一定是错的）：目标市场（本地／大湾区／全国／海外）、毕业届次与可入职时间、**明确排除的行业**、是否接受海外。
2. **每个板块必须挂证据**：来自母版哪段经历 / 哪个数字，并同时写「缺口 / 要补什么」。没有证据的板块不列。
3. **排序按「现在拿到面试的概率」**，不按理想度。
4. **板块落到具体目标公司类型**，并区分同名岗位在不同地区的差异。

### 时间线：不同市场 ≠ 同一套节奏（最容易踩的坑）

- **Summer Internship 常是给「倒数第二年」设计的**（部分 program 明确写「须在 X 年 11 月–Y 年 7 月毕业」）。**毕业当年的人不符合资格**，别照搬「暑期实习 = 校招前置」的惯性。
- 部分地区毕业当年的窗口是：**Graduate Programme（秋季招聘，入职次年）＋ 全年滚动的日常实习**。
- **投任何一个 program 之前先读它的毕业年份要求**，这是第一道筛子。

### 「应届」身份的有效期与打断条件

- **当届应届只有一次**：毕业前那一轮秋招。
- 毕业后仍在**择业期**：大量企业放宽到「**毕业两年内**」→ 同一岗位实际有两轮投递：当届轮 ＋ 宽限轮。
- ⚠️ **身份会被打断**：有正式全职工作并缴社保后，多数公司的「应届／毕业两年内」通道失效。所以当届轮是最优窗口，宽限轮不是无限期。
- **专项计划不吃应届身份**：政府／企业面向特定身份的培育计划、员额制招聘，卡的是**身份 ＋ 学历**，常明写「不设工作经验要求，应届亦可报考」→ 毕业后照投不误，且这类计划多为**每年固定档期**。

### 届次口径会随升学过期（校招资格的前提）

母版的届次 ＋ 毕业时间 ＋ 在读学位是**最容易过期的一栏**：用户升学后若没更新，简历会与所有校招的毕业区间要求自相矛盾。**每次求职对话先核这三栏**；口径改动用「本科毕业时间」与「硕士预计毕业」两行分开写，别合并成一个「毕业时间」。

### 面试练手：跨地区数据互通怎么判

判据是**「同一个 ATS ＋ 同一个身份标识（手机号 / 邮箱）」**，不是地区：

- 不同公司之间不共享数据 → 拿不相干的中小公司练手永远安全。
- 同一集团 / 同一套招聘系统会归集同一手机号 / 邮箱的全部投递：HR 能看到投了哪些岗、进度、以及**所有面试评价**；短期多投会被判「海投」静默降权。
- **投前 3 问**：① 两地是否同一个投递域名？② 是否要求同一手机号 / 邮箱注册？③ 官网有没有「一人 N 次投递机会 / 仅可投 1 个岗位」这类**集团级统一规则**？有 = 统一系统 = 互通，练手就换别家。

### 渠道分层与可靠性

| 层 | 来源 | 可靠性 |
|---|---|---|
| 1 | 公司官网 / 自家招聘系统（Workday、Greenhouse、Moka、北森…） | **唯一权威**。岗位是否还在、毕业年份要求、截止日期一律以此为准 |
| 1b | **招聘平台的「企业官方专题页」**（公司自运营的校招专题 ＋ FAQ ＋ 分项目页） | 与官网同级的一手来源。**决定投递策略的一次性规则只在这里写全**（每人几个平行志愿、投递后能不能改职位/简历、提前批与正式批的关系）；不同转载对同一项目的口径会互相矛盾 → **冲突时以专题页或官方公众号原文为准** |
| 2 | 聚合站（各类求职 App、应届生论坛、LinkedIn、JobsDB 等） | 只能用来「发现」，常有已过期、缺毕业年份要求、信息截断 |
| 3 | 校内就业中心 / 学校招聘系统 | 最准且大量岗位不公开，但**需要用户的登录态**，扒不了就让他自己筛 |

**规则**：聚合站只负责发现 → 每条都必须回官网核一次「还在不在 + 毕业年份要求 + 截止日期」，核不到就不进清单；**不得**把聚合站上的描述当事实写进推荐。

### 写任何经历前：先做素材考古（原始材料就在硬盘上）

用户的实习证明、结项 PPT、申请材料、旧 CV 里写着比他自述更细、更硬的事实。**不要凭他的一句话起草经历。**

- 搜索面：文档长期保存目录、下载目录、桌面。
- 抽文本的方法：`.docx`／`.pptx` 都是 zip —— 用 `zipfile` 读 `word/document.xml` 与 `ppt/slides/slideN.xml`，再 `re.sub(r'<[^>]+>',' ',x)` 去标签；老 `.doc` 用 `textutil -convert txt -stdout`。
- **按内容检索，不要只看文件名**：把项目关键词在多个目录里连 pptx／docx 内部文本一起搜一遍（全盘 `grep -r` 容易超时，按目录分批、限制深度）。命中后再逐页读完整正文，不要只看首页。
- 拿到材料后**先核三件事再动笔**：① 项目名与企业对不对；② **活动／项目的起止日期是否落在他该段任职期内**；③ 材料署的是谁（他本人产出，还是团队／公司提供）。

### 日历核对：写进某段经历的事，时间必须落在任职期内

凡是「我在 X 公司做了 Y 项目」这种写法，把 Y 的起止与 X 的起止并排放好再写。典型翻车：实习 7–8 月结束，而那个项目 11 月才上线 —— 面试官拿日历一算就穿。**这不是诚信问题，是算术问题**（用这个说法沟通，接受度最高，比讲道理有效）。

- **时间对不上不是把内容拆走的理由。** 正确做法是**并回对应经历段做子块 ＋ 脱敏 ＋ 不写独立日期**：
  - **位置**：接在**同产品线**的子块之后 —— 一条业务线连在一起读。
  - **脱敏**：子块标题去掉品牌名（写「某饮料品牌罐装扫码营销活动 · 效果分析」）。子块标题不要重复上一块已有的词。
  - **不与主段发生时间关系**：不给它单独的日期栏（主段行头的日期是共用的），也不写「独立分析案例」这种把它从主段摘出去的副题。
  - 正文里写「基于企业真实业务数据」，把性质讲清，不冒充任职期间的产出。
- 这样页面上不存在可校验的时间矛盾、不涉及编造劳务关系，而内容**归位到了它真正属于的那一段**。

### 用户的「建议区」协议

工作台类文件里可能要一节 `## ✍️ 我的建议区`（块间用 `<!-- SUGGEST:START -->` / `END` 包住）。约定：

- 用户**随便写、不分格式**（一条一行最好读），写完说一句「**读 NN 的建议区**」——这就是触发语，见到就去读那一节，把建议区里**所有**条目一次读完，不要只回应其中一条。
- 你**逐条回「✅ 已改 / ⚠️ 部分改（＋原因） / ❌ 不做（＋原因）」**，把办掉的那条**落进上面的正文**，并在「**已处理**」子块回填一行（含日期）。
- 原因要具体到可核查的事实（时间对不上、企业名记错、材料署名不是他），不要只说「这样不好」。

## 硬规则

- **不得编造**：没有证据的数字、头衔、经历、时间一律不写。用户给的数字直接照抄，不「优化」成整数。
  若用户选了饱和式路线（见上），**「不新增编造」≠「自我降级」** —— 不删他的词、不加限定语、不主动建议弱化。
- **写入前必须备份并展示 diff**。用户说「不用给我看」才能跳过展示，备份不能跳。
- **中英双语**：母版是中文主档时，英文版由中文母版派生，事实必须一一对应。英文版出现与中文版不一致的地方（如邮箱），标出来问用户，不要自行选一个。
- **联系方式**（电话、邮箱、地址）改动必须先确认再写。
- 旧版 `.docx`/`.pdf` 只读不写；新版本一律从母版生成。

## 常见坑

- 用户可能有多份历史 CV 散在多个目录；用 `mtime` 判新旧，别按文件名猜。文件名带 `CV` 的还可能是他人的（队友、同学），先按姓名筛。
- Word/PDF 导入的 CV 会丢掉加粗和分栏，读出来是「段落流」，不要据此判断版式。
- 中英两种表述（奖学金名称、公司全称）在母版里两者都留，导出时按语言取用。
- **删联系方式要「物理删字符串」，不能只标作废。** 校验脚本的「联系方式」块是把文件里出现的地址字符串全列出来 —— 若在同一行补一句「原 X 作废」，那个旧地址仍会被收录，等于没删。确认后直接改掉／删掉旧串（确认前仍然走主流程 A 的备份＋确认）。
- **用户自述的真实水平只进内部画像，不进母版。** 他若选择「母版保留原样」，不要自作主张地降级技能栏或加「基础」限定语；把「让简历变真」的补强路线写进投递台账（同一条铁律见 `job-search-method`）。
